# 📝 生成规范提交信息

按照 [Conventional Commits](https://www.conventionalcommits.org/) 规范生成 Git commit message。

## 📋 执行流程

| 步骤 | 操作 | 说明 | 必须 |
|-----|------|------|-----|
| 1️⃣ | **读取 skill** | 读取 `conventional-commit` skill 内容 | ✅ |
| 2️⃣ | **分析变更** | 运行 `git status` 和 `git diff` 了解当前变更 | ✅ |
| 3️⃣ | **生成 commit message** | 按照 skill 指令生成规范的 commit message | ✅ |
| 4️⃣ | **执行提交** | 使用生成的 commit message 执行 `git commit` | ✅ |

### 详细说明

#### 1️⃣ 读取 skill
读取 `.codebuddy/skills/conventional-commit/SKILL.md` 的内容并按照其指令执行。

**注意**：直接读取并执行 skill 文件内容，而不是调用 `use_skill` 工具。

#### 2️⃣ Conventional Commits 格式

```
<类型>[可选范围]: <描述>

[可选正文]

[可选脚注]
```

**常用类型**：
| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 Bug |
| `docs` | 文档变更 |
| `style` | 代码格式（不影响代码运行的变动） |
| `refactor` | 重构（既不是新功能也不是修复） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建过程或辅助工具变更 |

**示例**：
```
feat(web): 添加用户管理页面

- 新增用户列表页面
- 新增用户详情抽屉
- 新增用户创建/编辑表单

Closes #123
```

## 🎯 关键规则

### ✅ 必须执行
- 描述使用中文或英文，保持项目一致性
- 描述要简洁明了，首字母小写，结尾不要句号
- 如有 breaking change，在正文或脚注中以 `BREAKING CHANGE:` 开头说明

### ❌ 严格禁止
- 不要在类型中使用复数（如 `feats`）
- 不要写模糊的描述（如 `fix: 修了一些 bug`）
- 不要在 commit message 中包含敏感信息
