# 📝 生成规范提交信息

按照 [Conventional Commits](https://www.conventionalcommits.org/) 规范生成 Git commit message 并执行提交。

## 📋 执行流程

| 步骤 | 操作 | 说明 | 必须 |
|-----|------|------|-----|
| 1️⃣ | **加载提交规范** | 按本文档「Conventional Commits 格式」「关键规则」执行，无需外部依赖 | ✅ |
| 2️⃣ | **分析变更** | 运行 `git status` 和 `git diff` 了解当前变更，批量改动读 `CHANGELOG` 归纳主题 | ✅ |
| 3️⃣ | **安全检查** | 扫描待提交文件是否含真实密钥，确认 `web/.env` 未被跟踪 | ✅ |
| 4️⃣ | **生成 commit message** | 按本文档格式生成规范的 commit message | ✅ |
| 5️⃣ | **执行提交** | `git add` 后用 `git commit -F -` 提交，并验证结果 | ✅ |

### 详细说明

#### 1️⃣ 加载提交规范
本命令为自包含指令，直接按本文档「Conventional Commits 格式」「关键规则」「分析变更与执行提交」执行，无需读取任何外部规范文件。

#### 2️⃣ 分析变更与执行提交
- 用 `git status --short`、`git diff --stat`、`git diff --cached --stat` 看清改动范围；批量改动读 `CHANGELOG` 的 Unreleased 段归纳主题
- 提交前检查待提交文本是否含真实密钥 / 私钥 / 口令；`*.example` 里的占位符可以提交
- 默认 `git add -A` 提交全部工作区改动；用户指定范围时只暂存指定文件
- 用 `git commit -F -` 从 stdin 读入多行信息；提交后 `git log -1 --format='%B'` 与 `git status --short` 验证
- 不自动 push，除非用户明确要求

#### Conventional Commits 格式

```
<类型>[可选范围]: <描述>

[可选正文]

[可选脚注]
```

**常用类型**：
| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 Bug |
| `docs` | 文档变更 |
| `style` | 代码格式（不影响代码运行的变动） |
| `refactor` | 重构（既不是新功能也不是修复） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建过程或辅助工具变更 |

**示例**：
```
feat(web): 添加用户管理页面

- 新增用户列表页面
- 新增用户详情抽屉
- 新增用户创建/编辑表单

Closes #123
```

## 🎯 关键规则

### ✅ 必须执行
- 描述使用中文或英文，保持项目一致性
- 描述要简洁明了，首字母小写，结尾不要句号
- 如有 breaking change，在正文或脚注中以 `BREAKING CHANGE:` 开头说明
- 提交前检查待提交文件是否含敏感信息，提交后验证 `git log -1` 与工作区状态

### ❌ 严格禁止
- 不要在类型中使用复数（如 `feats`）
- 不要写模糊的描述（如 `fix: 修了一些 bug`）
- 不要在 commit message 中包含敏感信息
- 不要使用 `--no-verify` 或 `--amend`
- 不要自动 push

### 参数说明
`$1` 为可选的「提交类型 / 范围 / 简短描述」提示；未提供时按变更内容自动判断类型与范围。
