# ⏰ 检查定时器清理

**只报告不修改**。基于项目铁律——`setInterval`/`setTimeout` **必须**在 `onUnmounted` / `beforeUnmount` 中清理，否则路由切换后定时器仍会跑，造成内存泄漏与重复请求。

> 🎯 适用场景：提交前自检 / 修完一个含轮询的页面后做体检 / 定位"切换页面后还在请求"类 Bug 的根因。

## 📋 执行流程

| 步骤 | 操作 | 必须 |
|-----|------|-----|
| 1️⃣ | 在 `web/` 目录执行 `npm run lint:timer`（默认扫 `frontend/src`） | ✅ |
| 2️⃣ | 阅读输出——每条会标注：文件、行号、定时器类型（`setInterval`/`setTimeout`）、是否检测到对应清理 | ✅ |
| 3️⃣ | 对未检测到清理的，在对应组件补 `onUnmounted(() => clearInterval(timer))` | ✅ |
| 4️⃣ | 修完再跑一次确认零违规 | 推荐 |

## 🎯 检查规则

| 写法 | 工具判断 | 是否合规 |
|------|---------|---------|
| `const t = setInterval(...)` + `onUnmounted(() => clearInterval(t))` | ✅ 已清理 | ✅ |
| `const t = setTimeout(...)` + `onUnmounted(() => clearTimeout(t))` | ✅ 已清理 | ✅ |
| `setInterval(...)` 无变量保存，无清理 | ❌ 未清理 | ❌ |
| `setTimeout(...)` 一次性副作用且 < 任何路由切换时间 | ❌ 误报 | 🟡 需 AI 二次判断 |
| Model / Service 中创建定时器但未在 `dispose()` 中清理 | ❌ 未清理 | ❌ |

## ⚠️ 工具盲区（AI 二次核对）

工具是**纯静态扫描**，下列场景需 AI 人工判断：
- 通过 `useTimerStore()` 等 composable **间接管理**的定时器——工具看不到包装层，可能误报
- 一次性 `setTimeout(fn, 100)` 用于"下一帧执行"——业务上无需清理，工具会标为未清理
- 把 timer id 存在 Model / Store 字段里，在 `dispose()` 内统一清理——工具不识别 `dispose` 模式

## ❌ 禁止
- 直接用 `--fix` 让工具自动改（实验性，可能改坏副作用顺序）
- 看到工具报告就盲目加 `clearInterval`——先确认是不是误报
- 修复时**只清当前组件**，忘了 Model 里也持有的同一个 timer id

## 🔄 工具失败时的兜底

1. 检查 `web/node_modules/` 是否安装；如无则 `cd web && npm install`
2. 仍失败回退**手工巡检**：`grep_search` 搜 `setInterval\(|setTimeout\(` 逐文件核对是否有对应 `clearInterval`/`clearTimeout`
